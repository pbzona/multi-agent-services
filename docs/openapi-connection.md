# Connect Eve to the private commerce API

The canonical OpenAPI 3.1 contract generates shared types and an inline Eve connection for both role-scoped root agents. The runtime replaces the contract's relative server with the deployment-aware `COMMERCE_URL` service binding.

## Canonical source and generated artifacts

| File                                                      | Ownership                                                                 |
| --------------------------------------------------------- | ------------------------------------------------------------------------- |
| `packages/commerce-contract/openapi.yaml`                 | Canonical, hand-edited OpenAPI 3.1 source                                 |
| `packages/commerce-contract/scripts/generate-openapi.mjs` | Generator and drift checker                                               |
| `packages/commerce-contract/src/openapi.generated.json`   | Generated, sorted runtime document; do not edit                           |
| `packages/commerce-contract/src/openapi.generated.d.ts`   | Generated TypeScript `paths`, `operations`, and `components`; do not edit |
| `packages/commerce-contract/src/index.ts`                 | Public exports and runtime server override                                |

The generator performs four checks and transformations:

1. Parses `openapi.yaml` with `yaml`.
2. Requires `openapi: 3.1.0`.
3. Rejects external or invalid `$ref` values; every reference must start with `#/`.
4. Sorts the document, writes formatted JSON, and generates declarations with `openapi-typescript`.

Regenerate both artifacts after changing the canonical YAML:

```bash
pnpm openapi:generate
```

Verify that committed artifacts match the source without writing files:

```bash
pnpm openapi:check
```

The contract test also asserts the exact path, method, and `operationId` set:

```bash
pnpm --filter @repo/commerce-contract test
```

## Served contract and inline agent contract

`GET /api/openapi.json` returns `commerceOpenApi`, the generated canonical object with `servers: [{ "url": "/" }]`. The endpoint itself requires no bearer token, but the `commerce` service has no public Vercel rewrite, so it remains reachable only from bound services.

The agents do not fetch `/api/openapi.json`. Both import the generated JSON as a parsed object and pass an inline object to `defineOpenAPIConnection`:

```ts
const commerceOpenApi = withCommerceServer(process.env.COMMERCE_URL);

export default defineOpenAPIConnection({
  spec: commerceOpenApi,
  // Role-specific description, operations, auth, and approval follow.
});
```

An inline object pins tool generation to the contract committed with the agent build. It also avoids a contract-discovery network request and prevents a remote document change from silently changing the model-visible tool surface.

## Runtime `COMMERCE_URL` injection

`withCommerceServer(url)` returns a new top-level object and sets:

```ts
servers: url ? [{ url }] : [];
```

The helper does not mutate `commerceOpenApi`; its `paths` object remains shared. When each Eve process evaluates its connection module, `process.env.COMMERCE_URL` contains the URL generated by the caller-side Vercel service binding.

Do not put `COMMERCE_URL` in `.env`, Vercel project environment variables, or a deployment script. Vercel Services makes the value deployment-aware, so a preview agent reaches the commerce service from the same preview deployment.

If the binding is missing, the generated document has no server. Eve then rejects the connection because it cannot derive a base URL. Run `pnpm dev:services` for integrated local development instead of hardcoding a service URL. `pnpm dev` starts standalone component hosts and does not inject Vercel binding environment variables into either agent.

## Operation allowlists

Eve names generated tools `commerce__<operationId>`. Each agent exposes only the following operation IDs through `operations.allow`:

| `operationId`               | HTTP operation                             | Customer | Admin | Approval       |
| --------------------------- | ------------------------------------------ | -------- | ----- | -------------- |
| `listProducts`              | `GET /api/v1/products`                     | Yes      | Yes   | Not applicable |
| `getProduct`                | `GET /api/v1/products/{slug}`              | Yes      | Yes   | Not applicable |
| `getCurrentCart`            | `GET /api/v1/cart`                         | Yes      | No    | Not applicable |
| `setCartItemQuantity`       | `PUT /api/v1/cart/items/{variantId}`       | Yes      | No    | User approval  |
| `listCurrentCustomerOrders` | `GET /api/v1/orders`                       | Yes      | No    | Not applicable |
| `getCurrentCustomerOrder`   | `GET /api/v1/orders/{orderNumber}`         | Yes      | No    | Not applicable |
| `listInventory`             | `GET /api/v1/admin/inventory`              | No       | Yes   | Not applicable |
| `updateProduct`             | `PATCH /api/v1/admin/products/{productId}` | No       | Yes   | User approval  |
| `setInventoryLevel`         | `PUT /api/v1/admin/inventory/{variantId}`  | No       | Yes   | User approval  |

`GET /api/health` and `GET /api/openapi.json` have no `operationId` and are not in either allowlist. The model cannot discover or call them through the commerce connection.

An allowlist controls model-visible operations. Commerce independently enforces bearer-token roles on every data route, so hiding an operation is not the authorization boundary.

## Authentication flow

The connection turns a verified Eve session principal into a short-lived commerce bearer token:

1. The Eve channel verifies the `multi_agent_demo_session` cookie and requires the root's role.
2. Connection `auth` requires `ctx.session.auth.current.authenticator === "demo-session"` and `principalType === "user"`.
3. The resolver checks `role`, `workspaceId`, and the requested principal ID.
4. `createCommerceAccessToken` signs a five-minute JWT with the principal ID, role, workspace, issuer, and `commerce` audience.
5. `authorizeRequest` in Nitro verifies the JWT, checks the route's allowed roles, and passes only verified identity fields to the service layer.

The customer connection rejects any session that is not a verified `customer`; the admin connection applies the same rule for `admin`. Both the session JWT and commerce JWT use `DEMO_AUTH_SECRET` in this reference.

## Approval policy

Each connection normalizes a qualified tool name by taking the suffix after the last `__`. The policy then returns one of these statuses:

| Operation class    | Status                       | Effect                                                             |
| ------------------ | ---------------------------- | ------------------------------------------------------------------ |
| Explicit read set  | `not-applicable`             | Execute without an approval prompt                                 |
| Explicit write set | `user-approval`              | Park the Eve run until the user approves or denies the exact input |
| Anything else      | `{ type: "denied", reason }` | Do not execute                                                     |

The customer write set contains only `setCartItemQuantity`. The admin write set contains only `updateProduct` and `setInventoryLevel`.

Approval is an interaction safeguard, not authorization. The channel, connection resolver, and commerce route must still reject an invalid role or workspace. Production writes also need idempotency and audit controls appropriate to the operation.

## Input handling

Eve derives model-facing inputs from OpenAPI path, query, header, cookie, and request-body schemas. Path parameter names must exactly match placeholders such as `{variantId}` or Eve cannot substitute them.

Commerce validates inputs again with Zod and bounded request bodies. Significant write semantics include:

- `setCartItemQuantity.quantity` is an absolute final quantity; `0` removes the item.
- `setInventoryLevel.quantity` is an absolute on-hand quantity, not an adjustment.
- `setInventoryLevel.expectedVersion` implements optimistic concurrency.
- `updateProduct` accepts at least one of `name`, `description`, `category`, `status`, or `imageUrls`.

Never rely on the model-facing schema as the only validation layer.

## Response limitations in Eve 0.29.5

The installed Eve OpenAPI client returns every HTTP response to the model as:

```ts
{
  status: number;
  statusText: string;
  body: unknown;
}
```

Its current response behavior has these limitations:

- Non-2xx responses are returned as tool results instead of being thrown. Agent instructions must inspect `status` and the error body before claiming success.
- Response schemas in the OpenAPI document are descriptive; the client does not validate or coerce the returned body against them.
- Only a content type containing the literal `application/json` triggers JSON parsing. Empty bodies become `null`; other bodies, including malformed JSON, become text.
- The OpenAPI client itself does not paginate, retry, stream binary content, or enforce a response-size cap before reading `response.text()`.

The commerce API mitigates context growth with bounded `limit` values, opaque cursors, bounded fields, and small response schemas. Keep those bounds when adding operations. Recheck this section against the installed Eve runtime after an upgrade.

## HTTPS and loopback URL requirements

Eve 0.29.5 requires both fetched specification URLs and resolved operation base URLs to use `https:`. It accepts `http:` only when the hostname is loopback, such as `localhost`, `127.0.0.1`, or `::1`.

This repository uses an inline specification, so only the injected `COMMERCE_URL` server is checked. [Portless](https://portless.sh) 0.15.5 provides browser-facing HTTPS and HTTP/2 at [https://multi-eve.localhost](https://multi-eve.localhost) through a trusted local CA. That browser URL does not determine the protocol of the internal Vercel service binding.

In the default `pnpm dev:services` flow, Portless wraps the one public `vercel dev -L` endpoint. Vercel CLI can inject a loopback HTTP `COMMERCE_URL`, which Eve accepts because the binding hostname is local. `pnpm dev:services:raw` keeps the same local binding behavior while bypassing Portless's browser-facing TLS. Standalone agent hosts started by `pnpm dev` receive no Vercel binding URL.

A deployed binding is different. Vercel generates a deployment-aware runtime URL, and Eve requires that non-loopback URL to use HTTPS.

The preview acceptance test sent OpenAPI requests through the generated binding
and completed catalog, cart, inventory, and agent operations. Eve therefore
accepted the binding URL. Repeat this check after changing Vercel Services or
Eve versions.

## Change an operation safely

Follow this order to keep implementation, generated artifacts, and agent policy aligned:

1. Edit `packages/commerce-contract/openapi.yaml` with a unique `operationId` and bounded schemas.
2. Run `pnpm openapi:generate` and implement the matching Nitro route under `apps/commerce/server/routes/api`.
3. Add route authentication, workspace scoping, validation, sanitized errors, and concurrency or idempotency controls.
4. Add the `operationId` to only the required agent allowlist and classify it in the approval policy.
5. Run `pnpm openapi:check`, `pnpm test`, `pnpm lint`, and the relevant evals.

The full recipe is in [Extending the reference](extending.md#add-a-commerce-operation).
